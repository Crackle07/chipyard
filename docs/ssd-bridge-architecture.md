# SSD Block Device Bridge Architecture

This note captures the stable SSD block-device bridge interfaces and design
decisions. It intentionally omits session logs, debug transcripts, and run
history.

## Target-Side Block Device MMIO

The target-visible block device controller is instantiated by
`testchipip.iceblk.BlockDeviceController` at physical base address
`0x10015000`.

The target CPU programs requests through this register map:

| Offset | Register | Direction | Notes |
| --- | --- | --- | --- |
| `0x00` | `addr` | RW | Target memory address for DMA data. |
| `0x08` | `offset` | RW | Starting block-device sector. |
| `0x0C` | `len` | RW | Request length in sectors. |
| `0x10` | `write` | RW | `1` for write, `0` for read. |
| `0x11` | `allocate` | R | Reading submits the request and returns an allocated tag. |
| `0x12` | `nallocate` | R | Number of allocation slots currently available. |
| `0x13` | `complete` | R | Reading consumes and returns a completed tag. |
| `0x14` | `ncomplete` | R | Number of completed tags currently available. |
| `0x18` | `nsectors` | R | Backing-device size in 512-byte sectors. |
| `0x1C` | `max_req_len` | R | Maximum request length in sectors. |

Data movement between the target block device and the bridge uses 256-bit
beats. A 512-byte sector is therefore 16 beats, so widening from the old 64-bit
beat path reduces the number of per-sector beats by a factor of four.

## Host-Side Bridge Register Map

The FireSim host does not use the target MMIO map above. Instead,
`BlockDevBridgeModule` generates a CPU-managed bridge register file consumed by
the C++ bridge driver through `BLOCKDEVBRIDGEMODULE_struct`. Each struct field is
an MMIO address generated by Golden Gate, and field order must match the
`genROReg`, `genWOReg`, and `attach` order in
`generators/firechip/goldengateimplementations/src/main/scala/BlockDevBridgeModule.scala`.

The host-side register indices are:

| Index | Register | Direction |
| --- | --- | --- |
| `0` | `read_latency` | Host to bridge |
| `1` | `write_latency` | Host to bridge |
| `2` | `bdev_nsectors` | Host to bridge |
| `3` | `bdev_max_req_len` | Host to bridge |
| `4` | `bdev_req_valid` | Bridge to host |
| `5` | `bdev_req_write` | Bridge to host |
| `6` | `bdev_req_offset` | Bridge to host |
| `7` | `bdev_req_len` | Bridge to host |
| `8` | `bdev_req_tag` | Bridge to host |
| `9` | `bdev_req_ready` | Host pulse |
| `10` | `bdev_data_valid` | Bridge to host |
| `11..18` | `bdev_data_data_0..7` | Bridge to host |
| `19` | `bdev_data_tag` | Bridge to host |
| `20` | `bdev_data_ready` | Host pulse |
| `21..28` | `bdev_rresp_data_0..7` | Host to bridge |
| `29` | `bdev_rresp_tag` | Host to bridge |
| `30` | `bdev_rresp_valid` | Host pulse |
| `31` | `bdev_rresp_ready` | Bridge to host |
| `32` | `bdev_wack_tag` | Host to bridge |
| `33` | `bdev_wack_valid` | Host pulse |
| `34` | `bdev_wack_ready` | Bridge to host |
| `35` | `bdev_reqs_pending` | Bridge to host |
| `36` | `bdev_wack_stalled` | Bridge to host |
| `37` | `bdev_rresp_stalled` | Bridge to host |
| `38` | `bdev_target_cycle` | Bridge to host |

The 256-bit data registers are little-endian by 32-bit word:
`bdev_*_data_0` carries bits `[31:0]`, and `bdev_*_data_7` carries bits
`[255:224]`. The C++ driver stores one beat as four `uint64_t` words, which is
equivalent to eight `uint32_t` words in the same order on the host.

`bdev_target_cycle` exposes the bridge's target-cycle counter to host software.
It is present so a host-side latency model can align completions with simulated
target time instead of wall-clock time.

## FAME-1 Token Flow

`BlockDevBridgeModule` is a FAME-1 bridge. The bridge is designed to emit one
token per target cycle; `tCycle` increments when that token fires. The token
fire condition includes the normal `hPort` handshakes, bridge queue capacity,
and response-stall checks. If the host has not supplied data or a write ack by
the cycle when the timing model wants to release it, the bridge stalls target
token flow until the host catches up.

The target-side MMIO map and the host-side bridge register map are separate
interfaces:

- Target software uses the `0x10015000` register map to submit DMA-style block
  requests and poll completions.
- Host bridge software uses `BLOCKDEVBRIDGEMODULE_struct` to drain target
  requests and write responses into the FAME-1 bridge.

## Verilator SimBlockDevice Fix

The Verilator-only `SimBlockDevice` DPI model was fixed in the testchipip
submodule at `src/main/resources/testchipip/csrc/SimBlockDevice.cc`: the DPI
wrapper now drives `*data_ready = bdev->data_ready()`. The previous code drove
`data_ready` from `req_ready`, which could incorrectly couple request and data
channel backpressure. The same change widened the DPI data path in
`src/main/resources/testchipip/vsrc/SimBlockDevice.v` to 256 bits.

## Latency Model Direction

The committed bridge keeps the C++ model local to FireChip and file-backed. The
current timing knobs are the existing `read_latency` and `write_latency`
registers. The intended SSD timing work should extend this into a custom C++
latency model: first as a clear TODO or fixed policy, then as a parametric model
with an explicit configuration interface.

SimpleSSD was rejected for this port. The important reasons are architectural:

- It is event-driven and does not provide a clean synchronous estimator API of
  the form "given this request at this target cycle, return a completion cycle."
- Submitting to its HIL mutates internal device state, so using it as a pure
  latency oracle would require rollback, cloning, or accepting committed side
  effects during estimation.
- Carrying SimpleSSD upstream would add a large third-party source tree, config
  files, build-system hooks, and long-term maintenance burden to the bridge.

A purpose-built C++ model can be deterministic, small enough to upstream, and
matched to the FAME-1 token contract by using `bdev_target_cycle` directly.
